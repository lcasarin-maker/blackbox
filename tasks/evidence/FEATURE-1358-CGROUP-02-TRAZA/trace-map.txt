## Static call and accounting map

1. CUDA enters the driver through device ioctls; for UVM-managed allocations/faults, the open `nvidia-uvm` code provides the UVM path. Proprietary RM allocation internals are outside the open source. In the visible bridge, `nvidia/nv_uvm_interface.c:355-376` calls `rm_gpu_ops_memory_alloc_sys(...)`; `:450-474` calls `rm_gpu_ops_pma_alloc_pages(...)`. The declarations are `common/inc/rm-gpu-ops.h:45,52`. These show the boundary, not what the proprietary RM does after entry.
2. The open UVM code has explicit memcg context helpers: `nvidia-uvm/uvm_linux.c:37-55` obtains the memcg from an `mm`, activates it with `set_active_memcg`, and restores the previous active memcg at end. The compile-time guard is `nvidia-uvm/uvm_linux.h:169-208`: if `NV_IS_EXPORT_SYMBOL_PRESENT_int_active_memcg`, `UVM_CGROUP_ACCOUNTING_SUPPORTED()` is 1 and `NV_UVM_GFP_FLAGS_ACCOUNT` includes `__GFP_ACCOUNT`; otherwise helpers are no-ops and that macro omits the flag.
3. Two concrete UVM call sites in 580.178.04:
   - `nvidia-uvm/uvm_mem.c:572-594`: sysmem chunk allocations add account flags when support is compiled and `mm` is non-NULL, activate the context, allocate sysmem chunks, then restore context.
   - `nvidia-uvm/uvm_mmu.c:103-135`: user page-table sysmem allocation retains the VA-space `mm`, activates that memcg, adds `NV_UVM_GFP_FLAGS_ACCOUNT`, calls `alloc_pages`, then restores/releases the context.
   - `nvidia-uvm/uvm_va_block.c:3126-3129` activates `block_context->mm` around CPU population. This covers a CPU population stage, which may be reached while a GPU destination operation stages through CPU memory; source inspection alone does not prove that a specific CUDA API/run took it.
4. Static build evidence for the loaded 580 module: `/proc/kallsyms` contains `uvm_memcg_context_start [nvidia_uvm]` and `uvm_memcg_context_end [nvidia_uvm]`. Since those functions are inside `#if UVM_CGROUP_ACCOUNTING_SUPPORTED()` in `uvm_linux.c:37`, this supports that the loaded build compiled the context helpers. It does not establish which cgroup pointer was active in a specific execution or that a specific allocation reached these helpers.
5. Separate NVIDIA RM NUMA allocation path: `nvidia/os-interface.c:1664-1765` builds `gfp_mask` and calls `alloc_pages_node(nid, gfp_mask, order)` at line 1742. `NV_ALLOC_PAGES_NODE_SKIP_RECLAIM` is only the reclaim branch at lines 1735-1740; its constant is `common/inc/nv.h:805-807`. In 580 this function contains no `__GFP_ACCOUNT` branch. Thus this flag changes reclaim behavior and is not, by itself, a memcg accounting flag. The source tree does not expose proprietary caller decisions or `RmNumaAllocSkipReclaimPercent` implementation, so whether a given allocation enters this path remains unobserved.
6. The 615 comparison adds `NV_ALLOC_PAGES_NODE_DO_ACCOUNT` (`common/inc/nv.h:862-865`); `nvidia/os-interface.c:1874-1879` conditionally adds `__GFP_ACCOUNT` for that flag on Linux >= 5.14. The skip-reclaim branch remains separate at `:1881-1888`, modifying `__GFP_RECLAIM` and for high-order requests `__GFP_NOMEMALLOC`. The registry header `src/nvidia/interface/nvrm_registry.h:1200-1208` describes `RmNumaAllocSkipReclaimPercent` as the free-memory threshold for dropping `GFP_RECLAIM`; this is a reclaim policy, not proof of accounting ownership. This header is in the 615 comparison tree, not the installed 580 source.
7. Assembly interpretation: none used.

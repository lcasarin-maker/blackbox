# FEATURE-1358-CGROUP-03-NATIVO — evaluación parcial

Fecha de inspección: 2026-10-02. El objetivo fue cotejar soporte, kernel y mecanismos; no se cambió el driver ni el cgroup del host.

## Resultado de soporte

La fuente local `/tmp/blackbox-nvidia-615-source` declara NVIDIA 615.71.09, incluye GB10 con PCI ID `2E12 10DE 21EC`, y contiene las rutas nativas de registro/cargo dmem. El host enumera GB10 `10de:2e12`, por lo que el producto está en la tabla de dispositivos de esa fuente. En `kernel-open/nvidia/os-interface.c`, el driver 615 llama a `dmem_cgroup_register_region`, `dmem_cgroup_try_charge`, `dmem_cgroup_uncharge` y unregister; cuando `try_charge` devuelve `-EAGAIN`, transforma el límite excedido a `NV_ERR_RESOURCE_ACCOUNTING_HARD_LIMIT_EXCEEDED`. `src/nvidia/src/kernel/mem_mgr/memacct.c` registra región por GPU y precarga el uso ya ocupado. `video_mem.c` pasa por `memacctTryCharge` antes de construir una asignación de VideoMemory. Esto demuestra un mecanismo para las asignaciones que pasan por ese gestor; no demuestra que CUDA/PyTorch GB10 recorra esa ruta ni resuelve uso compartido, migración o doble contabilización.

El kernel local es 6.17.0-1032-nvidia, `CONFIG_CGROUP_DMEM=y`, y exporta las funciones requeridas en `Module.symvers`. La fuente 615 incluye el compile test `dmem_cgrp_id`; esa ruta permite detectar disponibilidad del ABI, pero no certifica comportamiento runtime. La versión instalada 580.178.04 presenta cero referencias a `dmem_cgroup`/`os_dmem` en `/usr/src/nvidia-580.178.04`; sí contiene helpers memcg de UVM, un mecanismo diferente y parcial.

615.71.09 exige que módulos abiertos, firmware GSP y componentes userspace provengan de la misma versión. La fuente pública solo trae los módulos, no un conjunto intercambiable de userspace/GSP. NVIDIA lista 615.71.09 como release aarch64 y la fuente declara aarch64 como arquitectura admitida. Así, la combinación kernel 6.17 + arm64 + GB10 tiene compatibilidad indicada por ABI/arquitectura/ID de producto, pero NVIDIA no publica aquí validación funcional de este modelo concreto ni de Ubuntu Noble con esa combinación. El runtime 615 sigue sin probar.

## Comparación ejecutable y retorno seguro

El arnés existente es `tools/cgroup_repro.py`; registra versión/boot/cgroup y snapshots antes, durante y tras liberar para `none`, `cpu_touch`, `cuda_malloc`, `cuda_malloc_managed` y `pytorch_empty`. Limita el tamaño a 32 MiB y usa `systemd-run --user --scope` con `MemoryMax=512M`. Correrlo crea scopes y ejecuta allocations CUDA; no lo ejecuté en esta captura porque el host ya tenía dos workloads GPU activos y el alcance aquí era de solo lectura. La comparación válida necesita el mismo kernel, boot/árbol de cgroups, arnés y pasos, primero 580.178.04 y después el stack 615 completo fijado. El criterio requiere controlar carga compartida y registrar también CPU positivo, GPU vacío negativo, rechazo bajo el límite, dos cgroups, liberación y sharing.

Procedimiento preparado, aún no ejecutado: conservar la selección y versiones de paquetes del host y los `.deb` 580 instalados; preparar artefactos del módulo 615 compilados contra headers exactos `6.17.0-1032-nvidia`; instalar en una ventana de mantenimiento solamente el paquete/runtime completo 615.71.09 arm64 (módulo, userspace y GSP alineados), y reiniciar para que módulo y firmware coincidan. Repetir la captura inicial y luego el arnés 01 bajo el protocolo de sus dependencias. Retorno: restaurar los paquetes/artefactos 580.178.04 guardados y el firmware 580 correspondiente, ejecutar `depmod`/actualizar initramfs según el paquete y reiniciar; confirmar con `modinfo`, `nvidia-smi` y el GSP. No instalar 615 junto al userspace 580 ni mezclar firmware, y no desplegar hasta tener autorización concreta y aprobación operacional. Estos pasos son un plan, no evidencia de instalación/rollback comprobados.

### Related UVM memory-saver scope

The separately pinned Memory Saver design (`christopherowen/dgx-spark-memory-saver`, commit `55816f0b5c88bbab3c0641f9d6f1d9fd36e5854d`, `docs/design.md`) packs eligible 256-byte UVM user leaf tables into 4 KiB slots backed by CPU pages of exactly 64 KiB. It keeps the original physical allocator for backing pages, preserving its existing memcg context and DMA/mapping accounting. This addresses page-table packing overhead; it does not change CUDA allocation charging. The current host's `getconf PAGE_SIZE` is `4096`, so the design's 64 KiB page-size guard is false and the optimization is inapplicable on this stack. The related R610 note (`docs/driver-610.md`) reports stock R610's large DMA transfer failure, reproduced with the patch removed; an independent RM alignment correction was needed for its tested setup. That result complicates driver-version selection and does not validate R610 as a safe substitute here. The coordinator's 43 hardware-free checks are software checks, not hardware/runtime evidence. These related findings do not change the open 615 runtime criteria.

## 379266 GB10: second CUDA process gets CUDA_ERROR_NO_DEVICE while another process holds a context (Compute Mode = Default) - expected?
Tema con respuesta oficial de NVIDIA que confirma que cuInit()=0 no basta y que la compuerta de sondeo es la mitigacion; da comando literal de sondeo, firma de dmesg del Xid 119 y el repo de repro. Se relaciona directamente con colapsos de GPU por rafagas de asignacion sobre memoria unificada, aunque el repo sin licencia indicada no es reutilizable tal cual.
- **Compuerta de serializacion: sondear cuInit() hasta que devuelva 0 antes de lanzar el siguiente proceso CUDA, con backoff; staff NVIDIA lo valida como mitigacion** — `python3 -c "import ctypes; print(ctypes.CDLL('libcuda.so.1').cuInit(0))" (100 = CUDA_ERROR_NO_DEVICE); backoff 1 s inicial / 10 s tope (sugerido por staff, post 2); mas un periodo de gracia fijo tras el teardown` (post 1; licencia: None; riesgo: cuInit()=0 es necesario pero NO suficiente: en un evento una rafaga de ~100 GiB tras pasar la compuerta llevo a fullchip reset (post 3))
- **Dos regimenes de CUDA_ERROR_NO_DEVICE: (a) ventana de teardown de decenas de segundos tras salir el proceso; (b) memoria unificada casi llena (~119/128 GiB comprometidos); el codigo de error enmascara un fallo de asignacion de GSP** — `sondeo de contexto con programa minimo: gcc cuprobe.c -o cuprobe -lcuda (cuInit, cuDeviceGet, cuDeviceGetName, cuCtxCreate_v2)` (post 3; licencia: no indicada; riesgo: El modo sleep de vLLM libera ~36 GB pero conserva el contexto; solo salir del proceso libera el dispositivo (post 1))
- **Firma de fallo Xid 119 por condicion de carrera rafaga de asignacion x teardown (o cerca de OOM): secuencia en dmesg _memdescAllocInternal -> NV_ERR_NO_MEMORY -> timeouts GSP_RM_ALLOC / GSP_RM_CONTROL -> Xid 119; estado de fullchip reset con spam de la asercion (status == NV_OK) || (status == NV_ERR_GPU_IN_FULLCHIP_RESET); recuperado con reinicio** — `dmesg (buscar Xid 119, GSP_RM_ALLOC, NV_ERR_GPU_IN_FULLCHIP_RESET); serializar usuarios de GPU` (post 3; licencia: None; riesgo: Un contenedor vLLM con restart-loop contra la GPU caida genero 358 aserciones consecutivas (post 5); la GPU limpia ~45 min con timeouts antes del colapso total)
- **NVIDIA MPS como alternativa para acceso concurrente (staff Neill)** — `no indicado (el comando no aparece en el texto)` (post 2; licencia: None; riesgo: vLLM gestiona la memoria de GPU de forma agresiva; probar con cuidado)
- Omision de NVIDIA: Staff NVIDIA (Neill, post 4) confirma que no existe API para consultar si el dispositivo esta listo para un nuevo contexto, que CUDA_ERROR_NO_DEVICE deberia ser CUDA_ERROR_OUT_OF_MEMORY en agotamiento de memoria unificada, y se comprometio a enviarlo como solicitud/bug al equipo de drivers.

## 359969 Driver 590.48.01 regression: UMA memory not released after CUDA process exit (works on 580.126.09)
Reporte con reproduccion y workaround concreto (drop_caches) mas declaracion de NVIDIA sobre version maxima soportada; la maquina usa 580.178.04, por lo que sirve como advertencia de no subir de rama 580. Respuesta de NVIDIA presente en post 2; post 3 ausente, post 4 cierre automatico.
- **Liberar memoria que el driver 590.48.01 no devuelve tras salir un proceso CUDA** — `sudo sh -c 'echo 3 > /proc/sys/vm/drop_caches'` (post 1; licencia: None; riesgo: Alternativas del mismo post: rmmod nvidia o reiniciar; vaciar cache afecta rendimiento transitorio)

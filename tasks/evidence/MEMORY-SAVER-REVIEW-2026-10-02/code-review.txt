Findings

1. [P1] `kernel-charges.bt` cannot report the charge owner or its attribution. It records `@pending_stack` and `@pending_comm` (lines 13-14), then accumulates per-stack/comm `@live_bytes` and `@live_count` maps (lines 24-33). It never reads/stores a memcg ID, cgroup path, PID, or owning `mm`; `comm` is the task executing the allocator and can describe a worker, not the request owner. Its only periodic output is `@outstanding_bytes` (line 49); the attribution maps and diagnostics are cleared in `END` (lines 50-53) without printing. Therefore this tool cannot satisfy task02's requirement to establish which cgroup owns real GPU-triggered allocations, even if the probes fire. It can at most report a scalar outstanding charge count/byte total from events it catches. Fixing this requires recording a stable cgroup identity at charge time and emitting attributed live counters and gaps/diagnostics. Do not use the present script as evidence of owner attribution.

2. [P2] Pool metadata is outside the existing UVM user-memcg accounting context. In both allocator patches the descriptor is allocated with `kzalloc(sizeof(*pool), NV_UVM_GFP_FLAGS)` before `phys_mem_allocate_sysmem_full_page(...)` (580 patch lines 99-108; 610 patch lines 99-108). The base 580 allocator switches to the user VA-space `mm` and adds `__GFP_ACCOUNT` only around `alloc_pages` (`/usr/src/nvidia-580.178.04/nvidia-uvm/uvm_mmu.c:112-126`). The pool backing page therefore retains the existing owner's charge, but the new descriptor is allocated outside that scope with flags that omit `__GFP_ACCOUNT`. This is a small kernel-metadata accounting gap, not a defect in the 64 KiB backing-page charge or in the packer’s claimed backing-storage savings. Any report built from memcg-accounted kernel-page probes will omit this descriptor.

Allocation, ownership, DMA, and reuse review

- The shared page belongs to a single `uvm_page_tree`; each table carries a pointer to its backing-page descriptor. New physical backing is allocated by the original user-tree allocator, which retains the `gpu_va_space` mm context and `__GFP_ACCOUNT` behavior in the 580 source (`uvm_mmu.c:112-149`). The pool releases that backing only when its used bitmap becomes empty, after the pre-existing tree tracker wait (`0001` lines 134-159; same logic in `0002`). Thus the physical page remains charged to the memcg selected at backing allocation for the full lifetime of any occupied slot. A per-slot memcg identity does not exist; slots are suballocations of one charged page.
- The DMA mapping is made once for the entire backing page by the original allocator. Each returned GPU physical address adds `slot * 4096`; existing CPU mapping uses `offset_in_page(phys_alloc->addr.address)` (`/usr/src/nvidia-580.178.04/nvidia-uvm/uvm_mmu.c:294-310`). The opt-in path requires coherent DMA and 64 KiB CPU pages (`0001` lines 80-86), zeroes the whole 4 KiB slot (`lines 123-127`), and the final free unmaps the original page address and full `PAGE_SIZE` before releasing the page (`lines 138-159`). Static inspection found no definite DMA offset/unmap defect within those explicit predicates. Hardware behavior outside them is not established here.
- The bitmap/list transitions are under `sysmem_pool_lock`; page allocation, tracker wait, mapping and final free are outside it. The normal free path waits on the tree tracker before taking the slot out of use (`0001` lines 134-148); reuse zeroes the slot (`lines 123-127`). Static inspection found no confirmed list/bitmap race or premature-reuse path in the reviewed flow. The run evidence in the repository records stress/readback tests, but this review did not rerun them.
- The 610 patch preserves the same 4 KiB slot, per-tree bitmap, backing allocation, memcg, offset, zeroing, and final-free design. The observed patch differences are the R610 page-tree HAL call signature/context and resulting hunk locations; there is no separately confirmed accounting or synchronization change in the supplied 610 patch.

4 KiB versus 64 KiB applicability

These are byte sizes. The patch uses a 4,096-byte slot for each eligible 256-byte leaf table. Under its exact `PAGE_SIZE == 65536` guard, `PAGE_SIZE / 4096 == 16`, yielding sixteen 4 KiB-aligned slots in one CPU page (`0001` lines 45-46, 80-86). On a 4 KiB CPU page the ratio would be one, so this exact design would not reduce the number of CPU pages; the explicit 64 KiB guard sends that case to the original allocator. A 256-byte slot is a possible separate design, not something this patch proves safe or portable. It would need evidence for GPU page-table address alignment, CPU/DMA mapping granularity and offset handling, cache-line/coherency behavior, tracker ordering under reuse, and target hardware. No claim that smaller slots are impossible follows from this review.

Relevance to cgroup tasks

For task02, the source supports the expected owner of a *backing page* (the user VA-space memcg active in the stock allocator), but the bundled tracer cannot observe/report that owner. A valid dynamic trace still needs an owner/cgroup identity, allocator flags, actual bounded API correlation, and negative controls. For task04, the review supports the narrow allocator change's preserved backing-page charge and calls out the uncharged descriptor; it supplies no recommendation to change RM skip-reclaim or `RmNumaAllocSkipReclaimPercent`, which are outside these UVM pool patches.

Concrete follow-up validation

- Extend the charge tracer to print and retain `cgroup_id` (or a stable memcg identity) at charge time, plus `pid/tid`, stack, page/order and success/failure counters; print attributed live bytes and uncharge/duplicate/order-mismatch diagnostics. Include a negative control whose expected owner delta is zero, and one CPU-page allocation expected to charge the designated cgroup. This would close the instrumentation gap for task02; outputting `comm` alone cannot distinguish request owner from worker.
- Run the 580 patch's bounded workload with two distinct user VA spaces placed in separate cgroups. Allocate/release leaf tables in each; check each cgroup's `memory.current` and relevant `memory.stat` while slots are held, after all but one slot are freed, and after the final slot is freed. This directly checks that each backing page is charged to the user VA-space owner and that the shared-page charge remains until the final slot.
- Repeat concurrent allocation/free with full-buffer readback while forcing interleaved transitions through empty, partially used, and full pool states. The repository records a concurrent/readback run, but the additional state-boundary check would specifically exercise `bitmap_full`, available-list removal/reinsertion, and final-page release under interleaving.
- For any proposed slot size below 4 KiB, validate table base alignment against the GPU's actual page-table requirements and DMA address behavior on each target, then repeat reuse/readback and cgroup-lifetime checks. Do not extrapolate from the present 4 KiB slot evidence.

## Failure and proposed mechanism

[NVIDIA forum thread 383624, posts 1 and 3](https://forums.developer.nvidia.com/t/dgx-spark-silent-hard-freeze-under-sustained-llama-cpp-inference-no-xid-oom-panic-10-second-telemetry-captured-warranty-ends-oct-14-requesting-cas/383624/3) reports a DGX Spark Founders Edition with DGX OS, kernel 7.0.0-1019-nvidia, driver 580.173.02 open module and BIOS 5.36_0ACUM018. During repeated hard freezes, the external 10-second telemetry stream recorded the last sample, while the synced kernel journal stopped with no Xid, NVRM, OOM, hung-task or panic message; EFI pstore was enabled and empty. A reply from another Spark owner says `netconsole` loaded with Secure Boot enabled on their unit: the module was signed with the build-time kernel key, and a dynamic target produced a “network logging started” message. The reply proposes a UDP listener and persistent modprobe or boot configuration.

`netconsole` sends kernel `printk` messages as they occur, outside journald. It can add an independent copy of kernel messages before a freeze. It cannot produce evidence when the kernel emits no message, and it does not recover the host. The responder tested module loading on their own Spark, not the reporting Founders Edition kernel and not through a real freeze.

## Blackbox coverage and gap

`FEATURE-1358-A2-EXPORTACION-EXTERNA` adds an optional UDP stream of selected GPU and host telemetry. That stream does not contain kernel `printk`. `bb scan` reads journal and pstore/kdump evidence, but the cited incident produced no message in those sources. Therefore the existing metric export and netconsole would provide different evidence paths.

## Scope

On the exact Blackbox GB10 kernel and Secure Boot configuration, inspect `modinfo netconsole`, module signature/trust, receiver addressing, firewall/network isolation and boot persistence. Determine whether the module can load without weakening Secure Boot or installing another driver. Reuse a designated, operator-controlled UDP receiver; keep the feature disabled until the destination and retention policy are configured.

Keep netconsole data separate from the existing telemetry payload. Restrict the target to an operator-controlled management network because kernel messages can expose host details and UDP is unencrypted. Record packet timestamps and receiver freshness. Do not interpret a quiet receiver as proof that the kernel was dead; distinguish network path failure, receiver failure, missing kernel messages and host failure.

## Closure evidence

On the target OEM/kernel/driver, capture a test kernel message in the receiver with Secure Boot enabled; verify the module signature, source/target interface and boot persistence. Exercise unavailable receiver and broken route controls, and ensure the failure is reported without disabling local journal/telemetry collection. Demonstrate that the collector can correlate boot identity and timestamps with Blackbox telemetry. Verify removal of the module and persistent configuration. Leave real-freeze coverage explicitly unverified unless an incident is captured.

## Risks and limits

UDP is unencrypted and unacknowledged. Persistent remote kernel logs need explicit access controls and retention. A network outage can remove this evidence channel at the same time as the host outage. Netconsole records emitted `printk` messages; it cannot prove why a silent hang occurred.

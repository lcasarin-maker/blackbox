- bb-root-run (voto de Luis 2026-10-14, "scripts sellados por hash"): runner root que solo ejecuta scripts de adopted/root-scripts/ cuyo sha256 esta en un manifiesto root-owned. Ficheros: bb-root-run.manifest.json (la propuesta; un test falla si queda vieja respecto a los scripts) y etc_sudoers.d_bb-root-run (la regla). El runner es tools/bb_root_run.py instalado tal cual como /usr/local/sbin/bb-root-run (root:root 0755, shebang `/usr/bin/python3 -I`, solo stdlib); lee los scripts de <home del usuario de SUDO_UID>/projects/blackbox/adopted/root-scripts (el checkout principal; el sitio no es frontera de seguridad, el sha256 si), deja salida y auditoria en /var/lib/bb-root-run (lo crea el runner, 0755) y usa /run como padre de su directorio temporal 0700. No toca docker ni systemd. Pasos, todos con sudo de Luis y desde el checkout principal (no desde un worktree: las rutas del comando salen de donde se corra):
  1. Leer lo que se aprueba: `python3 -m tools.bb_root_manifest --propose`. Imprime el manifiesto exacto, el texto completo de los seis scripts con su sha256, el sha256 del runner y, en la ultima linea, UN comando `sudo sh -c '...'`.
  2. Correr ese comando. Instala runner, manifiesto (/etc/bb-root-run/manifest.json, 0644) y sudoers (/etc/sudoers.d/bb-root-run, 0440) primero como `.nuevo`, compara el sha256 de cada copia YA de root con el impreso, pasa `visudo -c` y solo entonces los mueve a su sitio: si algo cambio entre la lectura y la instalacion, falla antes de activar nada (sudoers.d ignora los nombres con '.', asi que un `.nuevo` huerfano no da permisos).
  3. Comprobar el positivo: `sudo -l` lista la regla; `sudo -n bb-root-run dmidecode-sistema` sale 0 y deja /var/lib/bb-root-run/dmidecode-sistema-<ts>.txt y una linea en auditoria.jsonl.
  4. Comprobar los negativos (deben FALLAR): `sudo -n bb-root-run ../x` y `sudo -n bb-root-run 'a b'` los rechaza sudo mismo (pide contrasena; con -n sale con error); `sudo -n bb-root-run desconocido` sale 3; `echo '#' >> adopted/root-scripts/dmidecode-sistema.sh && sudo -n bb-root-run dmidecode-sistema` sale 3 (hash distinto), y despues `git checkout -- adopted/root-scripts/dmidecode-sistema.sh`.
  5. `python3 -m tools.bb_root_manifest --check` sale 0 ("aprobados iguales: 6, cambios: 0, could_not_run: 0"). Desde ahi, editar un script lo deja fuera hasta que se repitan los pasos 1-2.
  Sobre la regla de sudoers: el glob `*` de sudoers casa espacios y '/', asi que `bb-root-run [a-z0-9]*` dejaria pasar `a ../../x b`. Se usa la regex de sudo (>= 1.9.10; aqui 1.9.15p5) `^[a-z0-9][a-z0-9-]*$`, cuya clase no admite espacio ni '/': un solo argumento. El runner repite la guarda (exactamente un argumento, ^[a-z0-9][a-z0-9-]{0,40}$). Que sudo case la regex asi solo se emulo sin root; el paso 4 es la prueba real.
  Pasos, desde el checkout principal:
  1. Re-aprobar el manifiesto como en los pasos 1-2 de bb-root-run (de arriba): `python3 -m tools.bb_root_manifest --propose`, leer earlyoom-proteger.sh en la salida, correr el `sudo sh -c '...'` de la ultima linea.
  2. `sudo -n bb-root-run earlyoom-proteger`. El script se niega (rc 3) si /etc/default/earlyoom no es byte a byte el viejo (sha256 7e8a44b6...) o el nuevo; valida las regex con `earlyoom --dryrun` antes de escribir (rc 4 si no compilan); guarda el viejo en /var/lib/blackbox/etc_default_earlyoom.7e8a44b63203bbcab11613f82f32fbf565dbc789efe395b944965a5a2e3abcbc; escribe por temporal + mv; reinicia earlyoom y, si a los 3 s no esta `active`, restaura el viejo, reinicia y sale 5. Una segunda corrida con el contenido nuevo no hace nada y sale 0.
  3. Verificar: `sha256sum /etc/default/earlyoom` = 89fe78dade9afa4d8df1e51627d119b145102c3a21dd140a0f4a44f8b4b13c8e; `systemctl is-active earlyoom` = active; `tr '\0' ' ' < /proc/$(pgrep -xo earlyoom)/cmdline` lleva las regex nuevas; `journalctl -u earlyoom -n 5` muestra "Will avoid killing process names that match regex '(...|vllm|VLLM|docker|containerd|^bb-)'". El close_check de la ficha solo mira el fichero (el gate no admite tuberias); el proceso vivo se mira con el `tr` de este paso.
  4. Despues: `git mv adopted/pendiente-de-despliegue/etc_default_earlyoom adopted/system-config/etc_default_earlyoom` (sustituye al viejo) en el mismo commit que registra el despliegue.
  Revertir: `sudo install -m 0644 -o root -g root /var/lib/blackbox/etc_default_earlyoom.7e8a44b63203bbcab11613f82f32fbf565dbc789efe395b944965a5a2e3abcbc /etc/default/earlyoom && sudo systemctl restart earlyoom` (o, sin la copia, `sudo cp adopted/system-config/etc_default_earlyoom /etc/default/earlyoom` antes del paso 4); comprobar `sha256sum /etc/default/earlyoom` = 7e8a44b6... y `systemctl is-active earlyoom`.
